## Purpose

These standards ensure our Node.js/SvelteKit codebase is readable, maintainable, testable, and consistent across all team members and projects.

## Musts (Non-Negotiable)

### Code Quality
- [CODE-INT-1] **Use TypeScript**: All code MUST be written in TypeScript with strict mode enabled; avoid `any` types.
- [CODE-INT-2] **ESLint & Prettier**: Code MUST pass ESLint and Prettier checks before merging; use the project's shared config.
- [CODE-INT-3] **Small Functions**: Functions MUST be focused and single-purpose; avoid functions exceeding 30 lines unless justified.
- [CODE-INT-4] **Async/Await**: MUST use `async/await` for asynchronous operations; avoid callback patterns and raw Promise chains where possible.
- [CODE-INT-5] **No Magic Strings**: Configuration keys, API routes, and repeated strings MUST be constants or pulled from environment/config.

### Testing
- [CODE-INT-6] **Test Coverage**: New features MUST include tests using Vitest or Playwright; test critical paths and public APIs.
- [CODE-INT-7] **Tests Must Pass**: All existing tests MUST pass before merging; do not use `.skip()` to make builds pass.
- [CODE-INT-8] **Test Naming**: Test descriptions MUST be clear and follow the pattern "should [expected behavior] when [condition]".

### Error Handling
- [CODE-INT-9] **Explicit Error Handling**: Errors MUST be caught and handled explicitly; no empty catch blocks or silent failures.

## Shoulds (Strong Recommendations)

### SvelteKit Patterns
- [CODE-INT-10] **Server-First Data Loading**: SHOULD use `+page.server.ts` and `+layout.server.ts` for data fetching; prefer server load functions over client-side fetching.
- [CODE-INT-11] **Form Actions**: SHOULD use SvelteKit form actions for mutations; leverage progressive enhancement.
- [CODE-INT-12] **Type-Safe Load Functions**: SHOULD use `PageData` and `LayoutData` types generated by SvelteKit for type safety.
- [CODE-INT-13] **Error Boundaries**: SHOULD use `+error.svelte` pages for graceful error handling.

### Component Design
- [CODE-INT-14] **Composable Components**: SHOULD build small, focused components that do one thing well; compose larger UIs from smaller pieces.
- [CODE-INT-15] **Props Over Context**: SHOULD prefer explicit props for component communication; use Svelte context sparingly for truly global state.
- [CODE-INT-16] **Reactive Statements**: SHOULD use `$:` reactive statements for derived state; avoid manual subscriptions where possible.

### Styling with Tailwind
- [CODE-INT-17] **Utility-First**: SHOULD use Tailwind utility classes directly in markup; avoid custom CSS unless necessary.
- [CODE-INT-18] **Component Classes**: SHOULD use `class:` directive or `cn()` helper for conditional classes; avoid string concatenation.
- [CODE-INT-19] **Design Tokens**: SHOULD use Tailwind's theme values (colors, spacing, etc.) rather than arbitrary values like `text-[#123456]`.

### ShadCN & Radix Patterns
- [CODE-INT-20] **Use ShadCN Components**: SHOULD use ShadCN components for common UI patterns (buttons, dialogs, dropdowns, etc.); customize via Tailwind.
- [CODE-INT-21] **Radix Primitives**: SHOULD use Radix primitives for accessible, unstyled components when ShadCN doesn't have what you need.
- [CODE-INT-22] **Accessibility Built-In**: SHOULD rely on Radix's built-in accessibility features (keyboard navigation, focus management, ARIA); don't override unless necessary.

### Code Organization
- [CODE-INT-23] **Feature Folders**: SHOULD organize routes by feature in `src/routes/`; colocate related components, server files, and utilities.
- [CODE-INT-24] **Lib Structure**: SHOULD use `$lib/` for shared code; organize by purpose (`$lib/components`, `$lib/server`, `$lib/utils`).

## Architecture Patterns

### Recommended Patterns
- **Server Load Functions**: Fetch data on the server, pass to page via `data` prop
- **Form Actions**: Handle mutations via progressive-enhancement-friendly form actions
- **Stores for Client State**: Use Svelte stores (`writable`, `derived`) for client-side state
- **Server-Only Code**: Keep sensitive logic in `+page.server.ts` or `$lib/server/`
- **Zod Validation**: Validate form data and API inputs with Zod schemas

### Patterns to Avoid
- **Client-Side Data Fetching**: Avoid `fetch` in `onMount` when server load functions work
- **Prop Drilling**: Avoid passing props through many layers; consider context or composition
- **Inline Styles**: Avoid inline `style=` attributes; use Tailwind utilities instead
- **Non-Accessible Components**: Avoid building custom interactive components when Radix/ShadCN exists

## Examples

### Good: Server Load Function with Type Safety
```typescript
// +page.server.ts
import type { PageServerLoad } from './$types';
import { db } from '$lib/server/db';

export const load: PageServerLoad = async ({ params, locals }) => {
  const user = await db.user.findUnique({
    where: { id: params.id },
    select: { id: true, name: true, email: true }
  });

  if (!user) {
    throw error(404, 'User not found');
  }

  return { user };
};
```

### Bad: Client-Side Fetching When Server Load Works
```typescript
// +page.svelte - DON'T DO THIS
<script>
  import { onMount } from 'svelte';
  let user = null;

  onMount(async () => {
    const res = await fetch(`/api/users/${id}`);
    user = await res.json();
  });
</script>
```

### Good: Form Action with Validation
```typescript
// +page.server.ts
import { fail } from '@sveltejs/kit';
import { z } from 'zod';
import type { Actions } from './$types';

const schema = z.object({
  email: z.string().email(),
  name: z.string().min(2)
});

export const actions: Actions = {
  default: async ({ request }) => {
    const formData = await request.formData();
    const parsed = schema.safeParse(Object.fromEntries(formData));

    if (!parsed.success) {
      return fail(400, { errors: parsed.error.flatten().fieldErrors });
    }

    await db.user.create({ data: parsed.data });
    return { success: true };
  }
};
```

### Good: Conditional Classes with cn() Helper
```svelte
<script lang="ts">
  import { cn } from '$lib/utils';

  export let variant: 'default' | 'destructive' = 'default';
  export let disabled = false;
</script>

<button
  class={cn(
    'rounded-md px-4 py-2 font-medium transition-colors',
    variant === 'default' && 'bg-primary text-primary-foreground hover:bg-primary/90',
    variant === 'destructive' && 'bg-destructive text-destructive-foreground hover:bg-destructive/90',
    disabled && 'pointer-events-none opacity-50'
  )}
  {disabled}
>
  <slot />
</button>
```

### Good: Test with Vitest
```typescript
import { describe, it, expect } from 'vitest';
import { render, screen } from '@testing-library/svelte';
import UserCard from './UserCard.svelte';

describe('UserCard', () => {
  it('should display user name when provided', () => {
    render(UserCard, { props: { name: 'Alice', email: 'alice@example.com' } });

    expect(screen.getByText('Alice')).toBeInTheDocument();
  });

  it('should show placeholder when name is empty', () => {
    render(UserCard, { props: { name: '', email: 'test@example.com' } });

    expect(screen.getByText('Anonymous')).toBeInTheDocument();
  });
});
```
